# Pull-request files and submitted reviews

GitHub/GHES PR details now expose changed files, submitted reviews and a review composer. These requests use the connected account, validated repository selectors and PR number through the existing main-process provider boundary. Credentials stay in main; the Git utility accepts none of these public methods. No external review is sent merely by opening, previewing or closing a draft.

Changed files use pages of 100, with a maximum of 30 pages matching GitHub's 3,000-file limit. Every page checks the displayed head and base commits before and after fetching. A changed revision refuses the page and clears the file view; the user refreshes details to inspect the new revision. This detects observed changes, not an atomic server snapshot. Offset paging can still miss intermediate updates, and no immutable snapshot is claimed. File paths are display metadata, never local paths to open. API blob/raw URLs are ignored. Renames retain their previous path. Missing patches remain missing rather than implying no changes; large patches are explicitly truncated at 262,144 UTF-16 code units within the existing 4 MiB response cap.

The file list is virtualized, supports append/deduplication, arrow/Home/End navigation and Enter/Space selection. Patches use read-only CodeMirror with diff-line colors. Review pages use 100 records with the existing 100-page limit, deduplicate by review ID and display literal text, state, author, date and reviewed commit. Deleted authors and unsubmitted pending records are represented explicitly. Review refresh starts from page one. No provider markup executes or loads remote images.

The composer supports comment, approve and request changes. Comment/request-changes require nonblank text; all text is bounded to 65,536 UTF-16 code units. Preview shows the action, body and full reviewed head SHA before a separate Submit action. Main revalidates the account, head/base commits and open/nonmerged state immediately before sending. Draft PRs accept comments only. The POST explicitly supplies `commit_id` for the displayed head. GitHub can change after the preflight: this binds the review to that commit, but does not promise atomic approval of the current head/base or bypass branch protection.

Submission sends one POST and never retries automatically. Recognized client/auth/rate-limit rejections return a sanitized rejection. A lost, cancelled, server-failed or invalid acknowledgment after starting the POST returns an uncertain outcome, because the provider may already have recorded the review and notified participants. Success requires a valid submitted timestamp, matching commit and expected review state. Cancellation during preflight prevents the POST; cancelling after dispatch cannot retract a review. The UI preserves text on errors and offers a review-list check before explicitly returning from uncertainty to the draft. That check is informational, not automatic deduplication. A user can still choose to submit a second review.

The nested modal blocks parent interactions while composing. Closing an unsent text draft requires an explicit discard, and closing is disabled during submission. Component cleanup cancels outstanding work. Draft persistence and external-write recovery across app quit, reload or crash are not implemented by this slice and remain hardening work; the UI does not claim durable drafts.

MSW tests cover GitHub and Enterprise requests, patch bounds/omissions, metadata validation, pagination caps, stale head/base rejection, closed/draft restrictions, all three review actions, preflight cancellation and uncertain acknowledgments with exactly one POST. Electron acceptance retains the real main/preload/renderer path and verifies virtualized file paging/keyboard selection, read-only literal patches, draft discard, preview-before-send, stale rejection, commit-bound approval, refreshed reviews and uncertain-result inspection without resubmission. Encryption and provider HTTP are fixture boundaries; no live account review was sent.

Inline review comments/threads, markdown, PR creation/templates, merge, checks/issues and polling remain subsequent work. See [GitHub pull-request files](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files) and [GitHub review endpoints](https://docs.github.com/en/rest/pulls/reviews) for the public API parameters and limits informing this implementation.
