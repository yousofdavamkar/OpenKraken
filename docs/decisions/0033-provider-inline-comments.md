# Inline PR discussions and comments

The PR Comments section reads GitHub/GHES review comments through the existing account-authorized main-process provider boundary. Requests contain only a saved account, strict repository selectors, PR number and bounded page. Pages request 100 comments in created-ascending order and stop at 100 pages. The renderer deduplicates by comment ID and groups loaded replies with their original thread. Offset pages are not a snapshot: refresh reloads from page one, and a reply whose root is not loaded says so explicitly.

Normalized comments retain root/reply IDs, author, literal body, timestamps, file path, current/original commits, current/original line ranges and diff sides. Missing current lines with original lines are labeled outdated; file-level comments remain distinct. The UI does not infer resolved/unresolved state from REST comments. Hunks are truncated with an explicit marker at 262,144 UTF-16 code units, within the shared 4 MiB response-body cap. Arbitrary response links and HTML are not exposed as navigation or embedded content. Paths and hunks remain display data, never local filesystem instructions.

The discussion list virtualizes individual comment cards, including replies, so a long thread does not mount every reply at once. Each card shows its thread, location, literal body and expandable diff context. Reply actions always select the top-level thread ID. The composer uses the existing review modal's preview, explicit submission, pending-close protection, unsent-text discard and uncertain-outcome inspection. Opening or previewing a draft sends nothing.

Selecting a line in a provider patch offers a new inline comment. Hunk headers establish old/new file coordinates; deletions select LEFT and additions/context select RIGHT. Hunk headers and no-newline markers are not comment locations. Counters advance across separate hunks without treating patch display row numbers as file lines. The composer identifies the selected path, side, line and full reviewed head commit. Missing patches cannot be selected. This slice creates single-line comments; multi-line selection and file-level comment creation are not implemented.

Main validates the submitted shape and account, checks the displayed head/base commits and requires an open, unmerged PR. New comments send an explicit reviewed head SHA, path, line and side; the provider remains responsible for accepting that location. Replies first fetch the addressed comment through the configured API origin, validate its ID, require a top-level comment, and check its declared PR URL against the selected repository/PR. That URL is compared as data and never fetched. A reply to another PR or a nested reply ID is refused before writing. Users can reply to an outdated thread; the original context stays visible.

Only one POST is sent. Known client/auth/rate-limit rejections return fixed messages; cancellation, server failure or an invalid acknowledgment after dispatch reports an uncertain outcome. A successful new-comment acknowledgment must match the commit, path, side and line; a reply must reference the selected root. Both acknowledgments must declare the selected PR. Neither operation retries automatically. The review preflight is not atomic with provider writes, and cancellation after dispatch cannot retract a comment. The UI preserves the draft and lets the user inspect comments before explicitly returning to it after uncertainty. Durable drafts and crash/quit recovery remain M8 work.

MSW fixtures exercise GitHub and Enterprise comments, bounds, deleted authors, original locations, malformed anchors, cross-PR/nested-target refusal, changed commits, closed PRs, preflight cancellation and one-POST behavior after failed acknowledgments. Public IPC tests reject mixed/unknown targets, credentials, URLs, invalid coordinates and oversized/blank bodies; the Git utility rejects these provider methods. Electron acceptance verifies line mapping across hunks, literal comment text, root-directed replies, explicit confirmation, draft discard, refreshed discussions, uncertain-write inspection without duplication and cancellation on panel close. Tests replace only provider HTTP and OS encryption; no real account comment was sent.

[GitHub REST review comments](https://docs.github.com/en/rest/pulls/comments) documents list/create/reply endpoints, line/side coordinates, original locations and reply identifiers. The implementation uses those public endpoints through Octokit. Thread resolution, editing/deleting comments, multi-line/file-level creation and markdown presentation are not claimed by this slice. PR creation/templates, merge, checks and other providers remain separate M6 work.
