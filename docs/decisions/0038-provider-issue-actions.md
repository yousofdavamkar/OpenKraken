# Reviewed issue creation, comments and state changes

The Issues panel supports creating an issue from a title/description, posting a comment, closing an issue as completed or not planned, and reopening an issue. Each action uses a nested dialog with a separate review and confirmation. Creation reviews the selected host/repository and exact text. Comment and state reviews first load fresh issue details. Inputs freeze while a review is confirmed or a request is pending; changing text requires another review.

Existing-issue reviews return a SHA-256 digest of normalized issue details, including content, metadata and timestamps. Before writing, main reauthorizes the saved account and reloads the issue, rejecting any snapshot mismatch. This detects changes even when two edits have the same provider timestamp. PR targets, wrong issue numbers, locked comment conversations and requests for an already-current state are refused before sending. The hash is a preflight comparison, not a server-side compare-and-swap: another actor can still change the issue after the check. The PATCH sends only the intended state/reason, so unrelated title, body, labels or assignees are not overwritten by this action.

Creation sends only the reviewed title/body. Comment submission sends only the reviewed body to the selected issue. Close/reopen sends state and a compatible reason; duplicate linkage, assignment/label/milestone editing, comment editing/deletion and issue forms/templates are not included. GitHub remains the final permission and policy authority. No application Undo is claimed for these external actions.

There is one POST/PATCH per confirmed action and no automatic write retry. Successful acknowledgment must contain valid normalized data for the selected repository/issue and match the requested text or state/reason. Provider URLs are checked against the configured API host before displaying locally constructed URLs. An explicit client/auth/policy rejection is sanitized and requires a new review. Server errors, cancellation or malformed/mismatched acknowledgments after dispatch are uncertain, because the operation may already have completed. Raw response errors are never displayed.

The dialog retains drafts on stale/rejected/uncertain results. After uncertainty, it offers read-only inspection: paged issues across states for creation, paged comments for comment submission, and current issue state for close/reopen. Comment bodies can be expanded as literal text. A current observation does not prove who performed an action or that a missing item was never created. Matching current state blocks resubmission; otherwise the user must explicitly choose to review again and then separately confirm. Inspection never retries the write. Success or uncertainty refreshes affected list/details after closing.

Pending requests block dialog close but offer cancellation. Draft close uses Keep draft/Discard draft. Cancellation after dispatch cannot retract a remote action. Application quit/reload/crash recovery and durable issue drafts remain M8 work, alongside the existing external-write recovery work. No live provider issue was created, commented on or changed during development.

Strict IPC distinguishes creation, comment and state actions, bounds text and rejects missing review revisions, incompatible state/reason pairs, unrelated metadata, URLs and credentials. It keeps provider requests in main and rejects them at the Git utility boundary. The existing safeStorage credential envelope, identity/refresh checks, HTTPS host guard, redirect/cookie refusal, timeout and response limits remain in use.

MSW acceptance covers Enterprise creation, exact payloads, comments and close/reopen, changed snapshots including same-timestamp content edits, locked/no-op refusal, PR targets, cancellation before dispatch, and one-write behavior after server failures, foreign/malformed/mismatched acknowledgments, cancellation and explicit rejection. Electron acceptance uses the real main/preload/UI flow to verify review-before-write, preserved stale drafts, discard guards, rejection/review/success, comment refresh, state/list refresh, all three uncertain-result inspections without duplicate writes, deliberate review-again without submission, and cancelled review. Provider HTTP and OS encryption are fixtures; live accounts, actual keychain availability and cross-platform acceptance remain unverified.

Public references: [GitHub issue creation and update](https://docs.github.com/en/rest/issues/issues) and [issue comment creation](https://docs.github.com/en/rest/issues/comments#create-an-issue-comment).
