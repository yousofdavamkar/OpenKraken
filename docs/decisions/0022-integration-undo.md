# Integration Undo and Redo

Completed clean merge, squash, rebase, cherry-pick and revert operations record the initial and final HEAD, semantic index and tree IDs in the profile journal. Undo and Redo use native two-tree `read-tree -m -u` with submodule recursion disabled. This restores changed tracked paths while retaining unrelated local edits; a dry run refuses overlapping newer edits or untracked obstructions. It never uses the destructive `read-tree --reset -u` mode. See [Git read-tree](https://git-scm.com/docs/git-read-tree).

Before changing working files, verify both saved indexes' blob objects and reconstruct their tree objects. Missing historical blobs produce an explicit refusal without moving HEAD or changing files. Tree objects alone may have been pruned and can be rebuilt from the saved index. Compare-and-swap `update-ref` then moves the current branch or detached HEAD, and the private index is published under the normal index lock. Current HEAD and index must match the journal expectation. Skip-worktree and assume-unchanged flags currently require explicit clearing before integration Undo.

A pending recovery record precedes working-file updates. If updating the tree or moving the ref fails before the ref moved, attempt the inverse native tree update, retaining the recovery record on failure. A failure after moving the ref retains the record for recovery. Ref, index and filesystem changes are not an atomic transaction with external tools; tests cover ordinary native inverses and refusal paths, not a guarantee against arbitrary concurrent filesystem writers or filter side effects.

Native acceptance covers every listed integration mode, preservation of unrelated tracked/untracked edits, refusal of overlapping edits, and missing historical objects. The desktop flow exercises merge Undo and Redo before a mainline revert. Continuations of paused operations and pull are separate follow-up slices; no journal entry is advertised for their completed operation yet.
