# Provider credentials

M6 provider calls will run outside the renderer and directly against configured providers. The main process owns provider credentials; account UI and Git-service messages must receive only the metadata or narrowly scoped response they need. Provider tokens must not enter repository settings, logs, unencrypted profile data or renderer responses.

The credential vault uses Electron's asynchronous `safeStorage` API, as exposed by the installed Electron 45 types. The OS protects the encryption key; only ciphertext is written to private profile files. This is OS-protected encrypted storage, not a claim that each token is a separate OS keychain item. Linux explicitly permits the recognized libsecret/KWallet backends and refuses `basic_text`, `unknown` and unavailable encryption. There is no plaintext or silent memory-only fallback. Forgetting a credential remains possible while the keychain is locked.

Each future account identifier must bind a validated provider, origin and provider identity. Its hashed filename contains no token or display name; the encrypted envelope binds the account identifier again so copying ciphertext between account slots fails validation. Credential reads are bounded, reject nonregular files and use no-follow opening where available. Writes serialize within the main-process vault, create private temporary files and atomically rename them. Failed encryption preserves the prior file, and temporary files are cleaned. Key-rotation hints trigger re-encryption. Public errors omit native error text and credential material.

The fixture suite replaces only the OS boundary with authenticated encryption. It checks restart persistence, replacement/removal, file permissions on Unix, refusal of insecure/unavailable protection, swapped/corrupt/oversized files, rotation and preservation after encryption failures. These tests do not establish real keychain availability on macOS, Windows or a Linux desktop. Live provider authentication and Git askpass integration require separate acceptance; fixture tests do not establish them.

References: [Electron safeStorage](https://github.com/electron/electron/blob/v45.2.1/docs/api/safe-storage.md), [GitHub device authorization](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#device-flow). A GitHub device flow will require an explicitly configured application client ID; the implementation will not invent one or borrow another application's registration.

The first provider driver uses Octokit to validate GitHub/GHES tokens with `GET /user`. GitHub.com uses its separate API origin; Enterprise hosts use their own `/api/v3` endpoint. Configuration accepts only HTTPS origins without credentials, paths, queries or fragments. Requests omit cookies, refuse redirects, retain TLS verification, time out after 20 seconds and cap response bodies at 4 MiB. Octokit logging is disabled and public errors use fixed messages, never provider bodies or native request errors. Account identity requires a positive safe integer and binds the provider, normalized origin and stable user ID; reconnecting a renamed login updates one account.

The account service writes a bounded, validated metadata manifest separately from the vault, with at most 50 accounts. It validates credentials before saving and removes a new credential if saving its account manifest fails. Forgotten connections remove local ciphertext, not a remote token registration. Queueing protects profile writes from overlapping account operations. An abrupt process/filesystem failure between the credential and metadata writes can leave an orphan ciphertext file or a metadata entry requiring reconnection; cross-file crash recovery remains hardening work. No tokens are returned in account results.

MSW fixtures cover public/Enterprise identity, restart persistence, renamed logins, rejected tokens, origin validation, redirects, response bounds, cancellation and unsafe numeric IDs. The fixture transport refuses unhandled network frames. Public references: [GitHub authenticated user](https://docs.github.com/en/rest/users/users?apiVersion=2026-03-10#get-the-authenticated-user), [Enterprise API](https://docs.github.com/en/enterprise-server@3.17/rest/users/users?apiVersion=2022-11-28#get-the-authenticated-user), [Octokit requests](https://github.com/octokit/request.js/).

The desktop account dialog now routes list/connect/forget requests directly to the main-process provider service through strict shared IPC schemas. Tokens use an uncontrolled password field, are cleared before each request, and never return in account results. Network calls use a separate nonpersistent Electron session with cookies omitted. Closing setup or its window cancels validation; actual application Quit aborts provider requests and waits for its queue alongside the Git service within the existing shutdown deadline. Saved metadata remains visible offline or while OS protection is unavailable, but connecting requires protection. Forget removes the local connection and does not revoke a token remotely.

Electron acceptance replaces only OS encryption and network responses, retaining the actual main/preload/UI routing, profile writes and restart behavior. It covers rejected-token clearing, protected persistence, metadata-only results, offline restart, forgetting, unavailable protection and cancellation on dialog close. Existing unsaved-editor Quit/cancel behavior is rechecked. GitHub browser sign-in is covered by [the device-authorization decision](0027-github-device-authorization.md). Repository browsing is covered by [the picker decision](0028-provider-repository-picker.md) and native clone credential supply by [the Git authentication decision](0029-provider-git-authentication.md). Foreground fetch and reviewed push are covered by [provider remote authentication](0030-provider-remote-authentication.md). PR workflows and saved-account credentials for pull remain separate M6 work.
