# Provider credentials

M6 provider calls will run outside the renderer and directly against configured providers. The main process owns provider credentials; account UI and Git-service messages must receive only the metadata or narrowly scoped response they need. Provider tokens must not enter repository settings, logs, unencrypted profile data or renderer responses.

The credential vault uses Electron's asynchronous `safeStorage` API, as exposed by the installed Electron 45 types. The OS protects the encryption key; only ciphertext is written to private profile files. This is OS-protected encrypted storage, not a claim that each token is a separate OS keychain item. Linux explicitly permits the recognized libsecret/KWallet backends and refuses `basic_text`, `unknown` and unavailable encryption. There is no plaintext or silent memory-only fallback. Forgetting a credential remains possible while the keychain is locked.

Each future account identifier must bind a validated provider, origin and provider identity. Its hashed filename contains no token or display name; the encrypted envelope binds the account identifier again so copying ciphertext between account slots fails validation. Credential reads are bounded, reject nonregular files and use no-follow opening where available. Writes serialize within the main-process vault, create private temporary files and atomically rename them. Failed encryption preserves the prior file, and temporary files are cleaned. Key-rotation hints trigger re-encryption. Public errors omit native error text and credential material.

The fixture suite replaces only the OS boundary with authenticated encryption. It checks restart persistence, replacement/removal, file permissions on Unix, refusal of insecure/unavailable protection, swapped/corrupt/oversized files, rotation and preservation after encryption failures. These tests do not establish real keychain availability on macOS, Windows or a Linux desktop. Real provider connections, main-process routing, account UI and askpass integration remain subsequent M6 slices; the vault is not yet connected to them.

References: [Electron safeStorage](https://github.com/electron/electron/blob/v45.2.1/docs/api/safe-storage.md), [GitHub device authorization](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#device-flow). A GitHub device flow will require an explicitly configured application client ID; the implementation will not invent one or borrow another application's registration.
