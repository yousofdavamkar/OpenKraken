# 0077 — Opt-in crash summaries

The blueprint requires opt-in Sentry/OTel reporting with no code or personal data in payloads, and M8 requires a telemetry-free default build. Native memory dumps, exception messages, stacks, breadcrumbs and repository context cannot meet that payload constraint without retaining information the user did not agree to send.

Send a small Sentry event containing only a random per-report event ID, app release, operating-system family, architecture, an allowlisted process category and an allowlisted failure category. Do not initialize a general telemetry SDK or Electron crash-dump uploader. No user/session/machine identifier, code, path, account, command, exception object or server response body is collected. The HTTP receiver necessarily sees the connection's IP address; the consent dialog discloses that. This is diagnostic process-failure reporting, not usage analytics or detailed stack-based crash analysis.

The publisher may set `OPENKRAKEN_SENTRY_DSN` when building. Validate HTTPS, public-key/project syntax and the absence of passwords, queries and fragments before building, then embed the destination only in main. There is no runtime override and no renderer route for choosing a destination or submitting arbitrary report content. With no configured destination, the default build cannot send reports and its opt-in control is disabled. An actual deployment destination remains to be supplied by the project owner.

Consent is off by default and bound to a SHA-256 digest of the full configured DSN. Destination changes require new consent. A separate versioned file outside repositories uses private permissions, atomic replacement and revision checks; missing consent is off, malformed/unreadable/redirected consent stays off, and external changes detected before transmission stop reporting. The UI exposes the receiver and the exact data categories before the user chooses Apply. Opt-out immediately aborts pending transport and prevents further reports even if saving the preference fails; the UI then warns that persistence failed. Already transmitted bytes cannot be recalled.

Capture renderer failure events and known Git/terminal utility or GPU failure events in main. Ignore clean exits, intentional kills and unknown process/reason strings. Discard events observed before consent rather than waiting for an opt-in write. A consent generation check prevents an event crossing opt-out/re-enable boundaries. Permit one active request, one attempt per process/reason pair and at most five attempts per app launch. There is no retry or persistent report queue. Shutdown aborts delivery.

Use the [Sentry envelope protocol](https://develop.sentry.dev/sdk/foundations/envelopes/) with envelope-header DSN authentication, TLS verification, no cookies, redirect rejection and a five-second abort deadline. This requires a receiver supporting envelope authentication (Relay 21.6.0 or newer). Network/server failures expose only a bounded delivery state, and response bodies are discarded. The local HTTPS fixture validates the request format and privacy boundary; it is not acceptance evidence from a deployed Sentry project.

Tests cover default-off behavior, exact payload fields, persistence, destination changes, revocation during upload and failed preference writes, concurrent events, per-session limits, stale/corrupt/redirected consent, deadline aborts and strict main-only IPC. Linux desktop acceptance forces real renderer and Git-utility crashes against a locally trusted TLS receiver, checks persisted consent and opt-out, and verifies the disconnected default build. The fixture compiles its own main entry point with a fixed test receiver; production code has no test endpoint bypass or disabled TLS verification.

The initial increment did not report main-process death or JavaScript exceptions. [ADR 0078](0078-interrupted-session-and-javascript-reports.md) extends coverage with renewed consent, fixed-category JavaScript events and a local interrupted-session marker. Failures before reporting initializes, native memory dumps, live Sentry delivery, macOS/Windows crash-event evidence and beta acceptance remain outside this checkpoint. Existing crash recovery and operation-outcome handling remain separate from reporting.
