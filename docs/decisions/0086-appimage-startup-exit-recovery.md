# 0086 — AppImage startup exit recovery

The desktop handoff in ADR 0084 can install and launch a verified AppImage, but previously left the replacement installed when its executable failed to start or exited before startup acknowledgement. The native helper now supervises that first launch and can restore the exact retained predecessor once. Signature verification, explicit installation consent and the signed-release watermark remain unchanged.

The prepared transaction provides main with the predecessor's size/hash and the exact journal hash. Main passes those values, the signed replacement size/hash, original filename and literal profile argument to the copied helper. These values never come from renderer requests. Before launch, the helper requires its own process group and the expected live parent, completes the bounded handshake, waits for parent exit and rechecks replacement bytes. It launches the replacement in its own reserved group and retains the group identity while observing startup.

Normal startup acknowledgement still validates the actual version and installed image before removing the recovery directory. The helper observes that completed cleanup and exits. If executing the replacement fails, or its launcher exits before confirmation, recovery requires ordinary processes in the helper's group to be gone. After a launcher exits, the helper keeps observing its descendants. Restoration requires all ordinary group members to have stopped. Zombies have already exited. The helper disables the completed launcher channel while waiting for the group. Process inventory and reads are bounded, and uncertain inspection preserves files. The helper's live group leader prevents its group identity from being reused during this observation.

Restoration requires an owned, non-writable-by-others parent, a private recovery directory containing exactly the journal and predecessor, the journal hash from preparation, the exact installed replacement digest and the exact predecessor digest. File identities, sizes, modes, timestamps and link counts are rechecked; directory identity/ownership/mode must remain stable without rejecting unrelated directory-entry changes. Unexpected files, changed images, redirected paths or modified journals prevent replacement. Recovery atomically renames the retained predecessor back to the original filename, syncs the directories, and launches it once with the same profile. Its normal startup removes the remaining journal. No Git operation is retried and no network rollback watermark is reset.

The helper writes a bounded, private restoration notice through a synced temporary file and atomic rename in the existing update directory. It contains a fixed outcome only. Main validates it before showing a toolbar indicator and an Updates dialog notice; explicit dismissal removes only the unchanged validated file. A malformed notice cannot claim successful restoration. The notice persists across restarts and background checks. An unwritable notice location cannot prevent restoring the executable; in that case the visual notice may be unavailable.

## Slow or stalled replacement startup

After 60 seconds the helper switches from checking every 100 ms to checking every two seconds. A late startup acknowledgement finishes supervision. If the user closes a stalled replacement, the helper waits for the launcher and its ordinary descendants to exit, verifies both images and the journal, then restores the predecessor. This can also recover an unconfirmed application that exits on its own. A replacement that keeps running can retain the helper and backup for its lifetime. Indeterminate process-group inspection during slow polling ends supervision and preserves the files.

The helper opens the transaction directory before reporting readiness and holds that descriptor through supervision. After the parent exits it checks the path still refers to the same directory. Rollback checks the directory again before inspecting and restoring the images. Holding the inode binds this handoff to a single installation even if another transaction for the same two releases has identical journal and image bytes.

A dead helper, detached descendants, interruption during recovery and incompatible profile migrations still require separate recovery. Acknowledgement covers startup. Releases must preserve profile compatibility before acknowledging it.

Native tests cover failed execution, early exit, changed backup/journal/target, unexpected files, successful confirmation, and delayed descendant exit. They hold a launcher or descendant alive beyond 60 seconds, check both images while it runs, then verify restoration after exit or successful late confirmation. Separate tests replace the transaction directory after arming and after launch.

Controller tests cover persistent dismissal and malformed notice data. The packaged fixture can compile a replacement that exits from main before startup, then verify predecessor bytes/version, retained release sequence, journal cleanup, visible notice and dismissal. Both healthy and failed-startup modes are exercised with FUSE and extract-and-run. The `--delayed-descendant` fixture additionally leaves a three-second child behind when the replacement main process exits, and asserts that the predecessor does not start until that child has stopped. CI includes this case in both launch modes.

Linux process-state interpretation follows the [proc_pid_stat manual](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html); process-group semantics are documented in [kill(2)](https://man7.org/linux/man-pages/man2/kill.2.html). Native Windows/macOS helper stubs remain unchanged; cross-compilation is not runtime acceptance. Same-account attackers and physical power-loss behavior remain outside the evidence established here.

## Closing an update that stalls before the desktop mounts

After Electron is ready and has identified its AppImage, main starts a 60-second timer. If the desktop has yet to mount, it reads the private transaction journal. A matching version and architecture, with exactly the journal and the retained predecessor in the transaction directory, allow a native **Keep waiting** or **Close OpenKraken** prompt. It works before the first window exists and while the renderer is paused. The default and Escape keep waiting. A still-pending launch can prompt again after another minute.

If the user selects Close, main checks the journal again and exits the unconfirmed launch. The existing helper waits for process-group exit, verifies both images and the journal, and restores the predecessor only after those checks pass. A late renderer mount cancels the timer and dismisses an open prompt. Its first acknowledgement can enter once when the eight ordinary IPC slots are occupied. Later requests follow normal admission. [Electron native dialog cancellation](https://www.electronjs.org/docs/latest/api/dialog#dialogshowmessageboxwindow-options)

Three Linux x64 acceptance cases used disposable signed AppImages and a loopback HTTPS feed. On stable FUSE installs, native keyboard input closed a launch held in a profile read before window creation and another with JavaScript paused in Chromium. In the pre-window case, Escape kept the replacement running until the dialog returned a minute later. In both cases the runner checked the UI process that owned the dialog, the original and replacement image hashes, the relaunched version, release sequence, journal removal and rollback notice. A beta extract-and-run replacement completed mounting while its native dialog was open and eight ordinary IPC requests were outstanding. The dialog dismissed itself and the replacement stayed installed. This mechanism requires a responsive Electron main event loop and a readable journal. A blocked main thread or a failure before Electron is ready still requires external intervention.

## Interruption before publishing the restoration notice

The helper can exit after syncing the restored image and writing the complete private notice, before renaming the notice or starting the predecessor. On a manual relaunch, the restored app checks for the exact record written by the helper in `rollback-notice.tmp`. A complete record remains available in place across restarts until the user dismisses it. The app drops an incomplete scratch record. A published notice takes precedence and a malformed published notice still produces a storage error. Dismissal rereads the bytes at the observed path. If the helper finished its rename in the meantime, dismissal checks the published bytes before removing the notice there.

The stable FUSE and beta extract-and-run Linux x64 fixtures compile a disposable helper that exits immediately before the notice rename. Both fixtures verify the original image digest before manually reopening it, the boot order, retained signed sequence, startup journal cleanup and dismissal. This covers a predecessor containing the recovery change. Older installed builds continue to use their own startup logic. An interruption before the helper writes a complete notice can still restore the image without displaying a notice.

## Replacement with a missing desktop document

The packaged `--missing-renderer-document` fixture removes the replacement's initial HTML file before building and signing that AppImage. The installed replacement reaches the real window load, displays the startup error and exits after dismissal. The native helper can then restore and relaunch the predecessor. The fixture checks the original image digest, boot order, signed release sequence, transaction cleanup and restored app's notice. Linux acceptance uses the same failure path with stable FUSE and beta extract-and-run launches. ## Replacement with a missing renderer module

The `--missing-renderer-module` fixture reads the staged replacement's HTML, removes its referenced JavaScript asset, then builds and signs the image. The HTML still loads. The missing entry marker causes a fatal exit after the startup dialog is dismissed. Stable FUSE and beta extract-and-run launches both restored the exact predecessor, reopened the profile, retained the signed release sequence, removed the transaction and showed the restoration notice. Both used temporary signing keys and a loopback HTTPS feed. [Renderer startup check](0078-interrupted-session-and-javascript-reports.md#renderer-entry-evaluation)
