# Saved provider credentials for native Git

Provider account selection can authorize a native HTTPS clone. Main validates the connected identity (including device-token refresh) and binds the credential to a canonical repository URL on that account's configured origin. Renderer requests contain the account ID and clone options, never a saved token. A private main-to-Git-utility message carries the credential in memory for that operation. The utility owns the existing authenticated askpass socket; the native helper receives the answer over that socket and writes it only to Git's stdin pipe. Tokens are not command arguments, environment variables, remote URLs or repository configuration.

Saved-account mode requires an exact HTTPS origin and owner/repository path. The askpass broker matches Git's C-locale username/password prompt against that URL and account, rejects other hosts, paths, schemes, queries, usernames and SSH/proxy prompts, and never emits a renderer prompt. Credentials can answer more than once within the operation because partial/sparse clones can make subsequent lazy-fetch requests. Closing/cancelling the scope removes its credential reference and invalidates the socket capability. JavaScript strings are managed memory; this does not promise zeroization of every transient token copy.

Before cloning, native `ls-remote --get-url` resolves Git's URL rewrite rules without connecting. A changed URL fails before clone starts. Saved-account clones allow only the HTTPS transport and refuse redirects, including URL-specific settings that could override a generic default. Credential helpers are cleared for this mode so their approval/store callbacks cannot persist the provider token. The account username and path-aware credential matching are forced. Existing HTTP extra headers and cookie-file/save settings are cleared for the operation; certificate verification remains required. Trace environment variables and trace2 destinations are disabled. The protections apply to sparse checkout's possible lazy fetch as well as the initial clone.

Manual clone retains the user's existing credential helpers and SSH agents. Saved-account authentication is an explicit selectable mode, not a silent rewrite of a user's global Git configuration. All transport overrides are per-process command options. Trusted proxy and certificate-authority configuration can still apply. Foreground fetch, reviewed push/pull and remote branch/tag deletion use the checks in [provider remote authentication](0030-provider-remote-authentication.md).

Native tests use real Git, the compiled helper, a locally trusted HTTPS certificate, a deterministic repository and an authenticated fixture server. They verify scope matching, cancellation/expiry, no renderer prompts, no plaintext helper store or curl trace, URL-rewrite refusal and refusal of an authenticated redirect. These establish the local native transport boundary, not live GitHub authorization or real OS-keychain availability.

References: [Git credentials](https://git-scm.com/docs/gitcredentials), [Git configuration](https://git-scm.com/docs/git-config), [Git ls-remote](https://git-scm.com/docs/git-ls-remote).

The desktop picker selects saved-account mode by default and exposes a checkbox to use the existing Git credential helpers instead. Editing the URL clears the selected account. Main acquires the credential only after the destination dialog completes, rechecks cancellation before dispatch and never accepts a renderer-supplied credential. The private utility contract independently requires the credential URL to equal the clone URL. Cancellation during account validation cannot start a later native clone.

Saved-account clone progress exposes only fixed phase labels and percentages. Failure messages are fixed and do not forward remote diagnostics that could echo authentication material. The normal manual-authentication flow retains its current diagnostics. Electron acceptance uses real main/preload/utility routing and native verified HTTPS, replacing only provider REST responses and OS encryption. It checks successful authentication, absence of renderer authentication prompts or secrets in events/config/profile metadata, manual-helper selection, and cancellation before native transport starts. No live provider or real desktop keychain acceptance is claimed.

Provider-service and vault queues retain only completion promises, not resolved credential values. This avoids retaining the last decrypted token merely to serialize the next operation. Exact canonical prompt matching also rejects URL aliases such as traversal segments and an added default port.
