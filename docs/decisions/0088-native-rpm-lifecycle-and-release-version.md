# 0088 — Native RPM lifecycle and release version

An extracted RPM that runs on a developer machine does not prove native dependency resolution, upgrade integration or removal. Add package-manager acceptance in a disposable Fedora 43 container pinned by digest, alongside the existing payload/fuse checks and extracted-package desktop smoke. The script requires explicit test opt-in, a container marker, the expected distribution and root inside that container. It installs unsigned local test artifacts through DNF while retaining DNF’s verification of repository package signatures and TLS certificates. It never changes the host's package database. Bounded retries, a 30-second slow-transfer window at 50,000 bytes/second and an outer 12-minute deadline keep an unsuitable mirror from silently stalling the gate; DNF can choose another mirror.

The root `package.json` is the release-version authority, matching the existing installer producer. The bundle script must copy that version into its staged application metadata rather than hard-code `0.1.0`. An isolated upgrade fixture copies the built application into a temporary project, advances the fixture's minor version, then runs the actual bundle and installer CLIs. It reads the packaged ASAR's version and the installer manifest before allowing the native upgrade check. It never changes the workspace version or relabels an unchanged ASAR. Linux native compilation resolves the physical dependency directory before checking that node-gyp belongs to it, supporting the fixture's shared dependency link without weakening the containment check.

RPM owns `/opt/OpenKraken` and its subdirectories explicitly. FPM's default file-only list leaves unowned, empty application directories after removal. Use its explicit directory option for the private application tree; do not claim shared system directories or add a recursive deletion hook. The package manager removes empty owned directories and preserves unexpected files. The existing post-removal hook still distinguishes replacement from final removal so an old package cannot unregister its replacement's launcher.

The lifecycle test installs the declared dependencies, checks the launcher, desktop entry, icon, helper, CA store, and ELF shared-library resolution, then reinstalls the package. With a future-version fixture, it performs a real DNF upgrade, checks the installed version and changed application ASAR, and verifies that the launcher and fixture user data survive. Final removal must remove the application, launcher and package-owned integration while retaining user data. The artifact verifier also requires the RPM file list to own every private application directory represented in the payload manifest.

This is native Linux x64 package-manager evidence, not a graphical Fedora login session, a signed release, arbitrary profile-schema migration, every RPM distribution, or ARM64/Windows/macOS runtime acceptance. Both versions in the upgrade test use current source with different application release metadata. Real release identity, signing and beta distribution remain separate requirements. The test's root filesystem is disposable and the temporary upgrade fixture is retained for subsequent archive/UI checks and failure diagnosis.

RPM replacement/removal script semantics follow the [RPM scriptlet manual](https://rpm-software-management.github.io/rpm/man/rpm-scriptlets.7). This extends the lifecycle boundary in [ADR 0074](0074-linux-installer-payload-verification.md) and keeps the Debian native-module baseline from [ADR 0075](0075-linux-native-build-baseline.md).

The transfer bounds use DNF’s documented [minrate and timeout settings](https://dnf5.readthedocs.io/en/stable/dnf5.conf.5.html). Cached repository packages may be reused in a fresh container; they remain subject to DNF’s integrity and signature checks.
