# Provider-direct pull-request creation and templates

The PR browser now offers New pull request after choosing a saved account and target repository. The composer shows the configured host and target, accepts a source owner/repository/branch and target branch, and collects a title, description, draft flag and explicit maintainer-edit choice. Source defaults to the selected repository; maintainer edits default off. Branches must already be pushed. This workflow does not push changes, infer a fork, create a repository or silently grant edit access.

Preview resolves both remote branches through the configured provider and validates their returned names and commit IDs. Equal tips are refused. The composer then freezes the editable fields and displays the source/target repositories, branches, full commit IDs, text and flags before a separate creation action. Main reauthorizes the account and resolves both tips again before POST. A changed head or base requires another preview, preserving the draft. The provider remains authoritative for fork-network membership, permissions, branch protection and duplicate/no-change validation.

Same-repository requests use the literal source branch. Cross-repository requests qualify the source with its owner and include the source repository name, supporting fork names different from the target. The response must identify the expected source/base repositories, refs and commits, an open PR and the chosen draft state. Returned display URLs are constructed from the configured host, target selectors and validated PR number. API URLs are not followed.

GitHub creation accepts branch selectors, not a compare-and-swap condition for the previewed tips. A branch can therefore move after preflight. A response that no longer matches the preview is uncertain rather than falsely reported as the reviewed result; the app does not try to delete a potentially created PR. One POST is sent, without automatic retry. Recognized validation/auth/rate-limit rejections get sanitized messages; cancellation, server failure or a malformed/mismatched acknowledgment after dispatch requires inspecting existing PRs. The dialog provides bounded pages of existing PR summaries before the user can explicitly return to the draft. This is an inspection aid, not automatic deduplication or permission to retry without checking.

Repository templates are discovered from the default branch at a pinned commit. The reader traverses only the root, `.github`, `docs` and one `PULL_REQUEST_TEMPLATE` directory in each location. Default template filenames are matched case-insensitively with `.md`, `.txt` or no extension; files inside a template directory can have other names. Regular Git blob modes are accepted, including executable text; symlinks, submodules and nested folders are skipped. At most 50 templates are offered, and truncated tree results or multiple case variants of a template directory are explicitly marked incomplete. Directory responses have validated immediate-child paths and object IDs, and traversal is bounded independently of repository size.

Loading a selected template walks its path again in the pinned commit, requires a regular blob no larger than 65,536 bytes, verifies the returned blob ID/size/base64 content, and decodes strict UTF-8 without NULs. No local file is opened and no download URL is used. Templates render as literal text. Previewing one never edits the description; Replace description with template is a separate action. Repository template failures leave manual composition available. Account/organization community-health fallback templates and automatic branch-name suggestions are not implemented by this slice.

Titles are bounded single-line text, descriptions are bounded to 65,536 UTF-16 code units, and branch names reject ref syntax ambiguities and control characters. The typed public requests carry no API URLs, tokens or transport options and are unavailable to the Git utility. Existing HTTPS, redirect refusal, cookie-free requests, timeout, body caps, protected refresh and error redaction apply. Template reads and creation previews are cancellable; stopping after POST cannot retract a PR. The nested modal blocks parent interactions, requires discarding unsent edits before close and preserves drafts after failures. Draft persistence and external-write recovery across app quit/reload/crash remain M8 work.

MSW acceptance covers GitHub/GHES branch preview and creation, cross-repository parameters, same-repository parameters, stale head/base refusal, equal tips, preflight cancellation, uncertain acknowledgments without duplicate POSTs, template discovery, links, size/encoding validation, bounds and malformed paths. IPC tests reject invalid branches, unreviewed creation, arbitrary paths/URLs, secret fields and oversized text. Electron acceptance uses real main/preload/UI with synthetic provider/OS-encryption boundaries: template preview and explicit replacement, fork selection, draft preview, changed-head refusal, re-preview/success, list refresh, uncertainty inspection and cancelled preview. No live provider PR was created.
