# 0084 — AppImage desktop update handoff

The desktop now connects signed downloads (ADR 0082) to the AppImage transaction (ADR 0083). Installation is offered only inside a packaged Linux AppImage whose runtime executable, original image and embedded release version agree. Main derives these paths; renderer requests carry only a single-use installation identity. Other package formats still support verified downloads only. Default builds have no update feed.

Installation requires a native confirmation and no active Git/provider requests or live terminal. Main stops admitting new operations during preparation, while allowing update status/cancellation, draft persistence and shutdown acknowledgements. Existing unsaved-editor protection remains authoritative: choosing Keep editing discards preparation, preserves the original image and rotates the installation identity. Closing the Updates dialog does not cancel preparation.

Preparation revalidates the authenticated release, cache, staged image and predecessor. Arming makes the replacement executable, retains the original inode and syncs recovery state without changing the installed filename. This expensive work occurs before accepted shutdown. Commit rechecks release eligibility, storage, journal and image identities, sizes, timestamps, modes and link counts before atomic replacement. The existing 1,500 ms shutdown deadline is unchanged. This protects against ordinary external changes, not an attacker controlling the same account.

Restart uses a copy of the bundled native Go helper in the private update directory, outside the retiring AppImage mount. A real FUSE fixture showed that Electron's `app.relaunch` did not start the replacement even though replacement succeeded and a manual launch worked. The native helper acknowledges readiness before main exits, waits for its actual parent to exit (bounded to 20 seconds), then rechecks the signed length/hash and file ownership/type before executing the original filename directly. It passes one literal profile argument, uses no shell, and removes stale AppImage runtime paths from the inherited environment. Its IPC handshake is bounded; no renderer controls helper arguments or executable paths.

The new renderer's first mount asks main to acknowledge startup. Main checks the actual app version and installed hash before removing the predecessor. This recovery runs once per process so a later renderer remount cannot discard a newly prepared transaction. A failed acknowledgement preserves recovery files and disables further installation. The acknowledgement demonstrates that main and renderer reached startup; it is not a guarantee that every application feature is healthy.

Native acceptance builds two disposable hardened Electron AppImages, serves an ephemeral signed release over trusted fixture HTTPS, downloads it through the UI, cancels an unsaved-work restart, retries, and observes the new version acknowledging recovery. Test trust and dialog responses are compiled only into the fixture. Tests also cover changed cache/staged bytes, expired releases, stale installation identities and a helper that refuses changed executable bytes after the old parent exits.

Automatic checks, failed-startup supervision/rollback, production feed/key management, code signing and non-AppImage native installation remain separate work. If shutdown times out or the new executable cannot start, recovery files remain; this increment does not automatically restore or relaunch the predecessor. Linux fixture acceptance does not establish power-loss, other-filesystem, other-architecture or Windows/macOS release readiness.
