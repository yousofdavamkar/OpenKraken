# 0093 — Debian version upgrade acceptance

Extend the Debian lifecycle gate to require a real newer-version DEB. Same-version reinstall and direct calls to replacement guards remain useful checks, but neither establishes an APT upgrade through the old and new maintainer scripts. The existing fixture builder advances a private copy's release version, rebuilds the bundle and installer, and checks the actual bundled version. Both versions use the current implementation; this is not proof of migration across arbitrary future profile schemas.

The gate runs only with explicit disposable-container opt-in, a container marker, Debian 13 or Ubuntu 24.04, and root inside that container. It checks that both inputs are OpenKraken packages for the container architecture, the future version compares greater under dpkg's version rules, and the two archived ASAR digests differ. Refuse existing package state, application integration paths and fixture user data. These checks prevent accidental host use; environment/container markers are not a sandbox against deliberate bypass.

Before installing, create a draft sentinel in the fixture profile. After install, replacement-hook checks, same-version reinstall and actual APT upgrade, verify the package status/version, dpkg's installed-file checksums, exact expected ASAR digest, executable launcher, native helper, desktop entry, icon, CA store and ELF shared-library resolution. The slim image normally excludes documentation; pass a package-specific `--path-include` option so OpenKraken's documentation is installed and every shipped file remains subject to verification. Do not ignore missing-file reports. Check the sentinel at every stage. Removal must leave no application/integration path or dangling launcher; purge must remove residual package registration. Both must retain user data. Do not recursively erase remaining application files to make removal pass.

Write separate `release/installer-upgrade-deb.json`, `installer-upgrade-rpm.json` and `installer-upgrade-msi.json` pointers when building each format. Keep `installer-upgrade.json` as the most-recent fixture for existing local callers. CI uses the format-specific pointers, smoke-tests both newer Linux artifacts and supplies the newer DEB to its native lifecycle container. Building an RPM must not silently replace the Debian job's upgrade input.

APT repository authentication remains enabled. A local run may seed the fresh container with cached archives and signed indexes, with normal APT validation retained. Debian's container-only archive-cleanup hook can be removed inside that disposable image so `apt-get update` does not discard this cache. No host package database, release package payload, TLS validation or authentication setting is changed. Cache preparation failures and stopped transfer attempts are not passing lifecycle evidence.

## Installed desktop and profile continuity

After building the current DEB and the beta and stable upgrade fixtures, run `bash scripts/run-deb-lifecycle.sh debian` and `bash scripts/run-deb-lifecycle.sh ubuntu` from the checkout. Each command starts a fresh, digest-pinned rootless Podman container. It mounts the three artifacts, Node executable and test harness read-only. APT first installs the package with recommendations disabled. The fixture adds Xvfb, D-Bus and input automation after the dependency and installed-file checks. On Ubuntu it also compiles the shipped AppArmor profile offline. Kernel enforcement on a native Ubuntu login remains a separate check.

An ordinary user launches the installed desktop at each of the three package versions. The first version saves the Light theme through Appearance. Each upgraded version reads it through the same dialog. The fixture keeps the user's XDG configuration while creating fresh repositories for each version. It resolves the registered desktop entry and uses GIO to send a repository link to the running app, then approves the link in the UI. After removal and purge the fixture checks the digest of the settings file written by the app.

The prerelease and stable test packages use the same default profile with disconnected update configuration. Production beta-channel profile separation and migration between different settings schemas require separate evidence.

The upgrade/removal stages follow Debian's documented [maintainer-script installation procedure](https://www.debian.org/doc/debian-policy/ch-maintainerscripts.html), including invoking the old package's removal script during replacement. Package-specific file inclusion uses [dpkg's documented filters](https://manpages.debian.org/trixie/dpkg/dpkg.1.en.html). This extends [ADR 0075](0075-linux-native-build-baseline.md) and the real-version fixture from [ADR 0088](0088-native-rpm-lifecycle-and-release-version.md).
