# 0083 — AppImage update file transactions

Signed metadata and verified downloads (ADR 0082) must be followed by a recoverable installation operation. The AppImage file adapter stages, replaces, acknowledges or restores an owned image. This decision initially covered only the file transaction; [ADR 0084](0084-appimage-desktop-update-handoff.md) now connects it to desktop install IPC, accepted shutdown and native restart. Complete automatic update acceptance is not claimed.

The adapter accepts paths only from its main-process caller. The desktop handoff derives the target from the running packaged AppImage, revalidates signed release eligibility and requires explicit restart consent. The adapter independently re-hashes the cache and the staged copy against the authenticated digest/size, checks ELF/type-2 AppImage headers and architecture, and never executes a file to discover its format. Header checks identify the format; the release signature, verified by the caller, establishes authenticity.

Staging creates one exclusive private directory next to the original filename: `<image>.openkraken-update`. Its fixed files are `next.AppImage`, `previous.AppImage`, `transaction.tmp` and `transaction.json`. It cannot overwrite an existing transaction. The target and parent must be owned by the current Linux user and not writable by another account. Symlinks, extra hard links, malformed journals, changed images and unrecognized recovery files fail closed. A root-owned or otherwise unsupported location needs a separate installation method; no elevation is attempted.

Copying is bounded by the signed size (at most 2 GiB), cancellable and followed by a second digest check. The journal binds target basename, replacement version/architecture, and both image sizes and hashes. It is written privately, synced and atomically promoted before replacement can begin. Arming rechecks both images, makes the verified staged image executable, retains the old inode with a hard link and syncs recovery state. Commit rechecks the journal and file identities/metadata, then atomically renames the replacement over the original filename and syncs both directories. Arming can run before shutdown to keep large hashes outside the exit deadline; commit arms automatically when called alone. The old image remains available until a later startup acknowledgement or explicit rollback. Each transaction retains at most one staged/replacement image and one predecessor; the download cache is separately bounded.

Recovery discards incomplete copies that have no committed journal or backup, and discards prepared transactions while the original hash is still installed. It validates every recognized existing file before cleanup and preserves unexpected files. When the installed hash matches the replacement, acknowledgement additionally requires the actual running app version to match the journal. Cleanup can itself be resumed after interruption. Explicit rollback restores only the retained predecessor of the exact installed replacement; it refuses to overwrite an externally changed target. Network rollback protection remains separate and is not reset by this local recovery operation.

This does not defend against an attacker controlling the user's account, nor does normal process-interruption testing establish power-loss durability on all filesystems. Copying/staging occurs before shutdown. The desktop handoff preserves cancellation and unsaved-work protections and restarts after accepted shutdown; [ADR 0086](0086-appimage-startup-exit-recovery.md) adds restoration after failed execution or early startup exit. Recovery of hung or interrupted updates remains open. Windows MSI, macOS DMG/ZIP and Linux DEB/RPM remain separate native installation paths.

The native acceptance script builds two minimal, independently authored AppImages using the existing pinned tool/runtime. In both FUSE and extract-and-run modes it replaces an image while its old process is alive, verifies that process still reads its old files, launches the replacement, restores and launches the predecessor, then retries and confirms. These are real AppImage runtime/file operations, not Electron application restart acceptance. CI runs this check after constructing the AppImage installer; remote CI execution remains unverified.

References: [AppImage runtime environment](https://docs.appimage.org/packaging-guide/environment-variables.html) identifies the original image path; [Electron app lifecycle](https://www.electronjs.org/docs/latest/api/app) describes relaunch and accepted quit behavior. Desktop handoff implementation and its acceptance bounds are recorded separately in ADR 0084.

## A newer release containing the installed image

Before creating the transaction directory, the adapter checks the size and SHA-256 of the running image and the verified candidate. If they match, the Updates dialog reports the duplicate and keeps the application open. The accepted release sequence remains on disk. A publisher can issue a corrected package at a higher sequence, and the user can check again in the same session.

Older builds could leave a journal whose predecessor and replacement digests were identical. When the installed image matches the recorded predecessor, startup validates every remaining file and its link count and discards the obsolete transaction. Tests cover an interrupted stage, a linked backup before rename, and a backup after rename. In each case, changing the retained file prevents cleanup until its expected bytes are restored.

Run `xvfb-run -a node scripts/verify-update-restart.mjs --unchanged-image` after building on Linux. The fixture signs the initial version at sequence 1, advertises the same image as a newer version at sequence 2, then publishes the corrected bytes at sequence 3. It checks the dialog, installed digest, boot history, journal and release watermark through restart.
