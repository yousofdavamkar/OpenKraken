# Provider pull-request browsing

The first PR workflow is a repository-scoped list and detail panel. The user chooses a connected account and repository using the existing provider picker; this does not depend on a local clone. The account fixes the HTTPS origin, while strict owner/name segments and a positive safe-integer PR number identify the resource. Renderer requests cannot supply an API URL, token, arbitrary query or transport option. Main validates/refreshes the account before each request and returns only validated PR fields.

GitHub/GHES lists use `pulls.list`, an explicit open/closed/all state filter, created-descending order and 100 results per page. The existing 100-page cap bounds a list at 10,000 rows. API pagination URLs are not followed. Offset pages can change as PRs are created or updated, so the UI deduplicates by PR number and provides a full refresh rather than claiming an immutable snapshot. Closed lists include merged PRs, distinguished by their merge timestamp. The detail call uses `pulls.get` and requires its response number to match the requested number.

Responses share the existing timeout, cancellation, HTTPS, redirect refusal, cookie-free session, bounded-body and sanitized-error behavior. Metadata and counts have explicit schema limits; descriptions are bounded to 262,144 UTF-16 code units within the 4 MiB response cap. Branch SHAs, dates and PR states are validated. Canonical display URLs are built from the connected origin, selected repository and validated PR number; API-provided URLs are ignored.

The desktop list is virtualized, supports append paging, search of loaded titles/numbers/authors, arrow/Home/End navigation and Enter/Space to open details. State changes reset the list and details. Repository changes and closing the panel cancel outstanding list/detail requests, with component lifetime guards preventing late responses from replacing the current view. List and detail failures have explicit retry controls. Refreshing clears stale detail content while loading its replacement.

Details show state/draft/merged status, author, source/base labels, timestamps, commit/file/change counts, description and commit IDs. An unknown mergeability result remains unknown; the display does not imply branch-protection or review approval. Descriptions render as literal text with preserved whitespace. They cannot execute HTML, embed images or navigate the renderer. Files/patches and submitted reviews are added in [ADR 0032](0032-provider-pull-reviews.md). Markdown rendering, inline review threads/comments, creation/templates, merge, checks/issues and polling remain subsequent PR work.

MSW tests exercise account authorization, GitHub and Enterprise endpoints, paging limits, response validation, deleted authors, canonical URL construction, failure redaction and cancellation. Electron acceptance keeps real main/preload/UI and profile persistence while replacing provider responses and OS encryption. It verifies paging/deduplication, bounded DOM rows, search/keyboard selection, detail retry, literal markup, state changes, repository-switch cancellation and cancellation on close. This is fixture acceptance; live GitHub sandbox-org PR acceptance remains outstanding.

Public reference: [GitHub REST pull requests](https://docs.github.com/en/rest/pulls/pulls), specifically list/get request parameters and response fields. Implementation uses the existing Octokit driver; no server component is introduced.
