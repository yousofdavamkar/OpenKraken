# Saved accounts for existing Git remotes

The existing-remote flow supports foreground fetch and reviewed push. The public `providerGit` request carries a saved account ID and a strict operation descriptor. Fetch carries the remote name and displayed revision; push review carries a selection and revision; execution carries the reviewed push plan. It cannot carry a credential or background flag. The plan includes a display URL, but native transport always resolves its target from Git configuration rather than trusting that field. Existing helper/agent-based requests remain available.

Main asks the Git utility to resolve the configured target without network access. Saved-account mode requires one canonical HTTPS owner/repository URL; URL rewrites and credential-bearing/non-HTTPS URLs are refused. Main compares the resolved remote/configuration revision with the reviewed revision before loading a token, validates the account identity and configured origin, and passes the credential plus resolved revision to the utility over its private contract.

The Git service rechecks the remote URL and configuration/tracking-ref revision under the repository queue immediately before fetch. Changed settings or refs require reloading/reviewing the remote. Native askpass remains bound to the exact URL/account; redirects, credential helper storage, HTTP credential headers/cookies and tracing are restricted by the same per-operation safeguards used for saved-account clone. Only HTTPS is permitted. The existing atomic fetch, refspec, pruning and tag behavior is retained.

The main-to-utility target lookup uses its own request ID but is attached to the foreground cancellation signal. Cancellation propagates through lookup, account validation and native execution. Saved-account failures and progress use fixed diagnostic fields so remote output cannot expose authentication material. Automatic fetch continues to use the existing noninteractive helper flow; this request does not silently opt users into background use of saved accounts.

Native tests exercise real verified HTTPS fetch and validate imported tracking refs, scope matching and refusal before network use when a remote changes. The shared contract rejects renderer-supplied credentials and arbitrary target overrides, and keeps target resolution private. Pull and remote-deletion support still need their corresponding upstream and reviewed-plan checks before using this boundary.

References: [Git fetch](https://git-scm.com/docs/git-fetch), [Git remote](https://git-scm.com/docs/git-remote), [saved-account transport safeguards](0029-provider-git-authentication.md).

Manage remotes now provides a Fetch authentication selector. It defaults to the existing helpers/SSH agent, lists connected accounts using metadata only and disables saved-account choices while OS protection is unavailable. Selecting an account affects foreground fetches in this dialog and is not silently persisted as a global or background preference. The displayed remote revision travels with the request; stale dialog state is rejected before provider validation, while a change during validation is rejected by the utility before network use.

Electron acceptance performs real HTTPS fetch through main, preload, the Git utility and the native helper, verifies imported refs, changes the remote during account validation, retries stale dialog state, reloads settings and cancels a subsequent validation. It checks that rejected/cancelled attempts never contact the Git server. Native coverage also refuses multiple fetch URLs, non-HTTPS/credential-bearing URLs and rewrite rules.

Push uses the configured push URL (falling back to the fetch URL only when no push URL is configured). Review and execution both re-resolve this direction before credential access and check it again under the repository queue. Review carries the displayed remote revision; execution carries the existing push plan token. The existing local-source guard and exact remote-tip force-with-lease remain mandatory. No unchecked force path is introduced.

The Push authentication selector defaults to Git helpers/SSH agent and is locked after review. Review again reloads remote metadata, including after push sets upstream or updates tracking refs. A separate Reload remotes action recovers stale pre-review state. Saved-account errors expose fixed rejected-push, stale-plan and rejected-lease diagnostics; upstream-setting failures after a successful push return a fixed warning without forwarding remote output.

Native HTTPS coverage verifies that review uses the push URL and refuses changed settings before network use. A Gitea-backed Electron test performs a saved-account push and sets upstream, rejects a divergent normal push, refuses a force-with-lease after a competing remote update, then succeeds after explicit re-review. It verifies remote tips and absence of renderer authentication prompts or credentials in events and repository configuration. Provider REST and OS encryption are fixture boundaries; native Git, HTTPS and the receive-pack server are real.
