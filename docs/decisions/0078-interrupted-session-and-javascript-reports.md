# 0078 — Interrupted-session and JavaScript reports

[ADR 0077](0077-opt-in-crash-summaries.md) establishes the fixed-field, opt-in reporting boundary. Extend its coverage without collecting exception text or native memory.

After the single-instance lock succeeds, initialize reporting before the rest of the ready-time startup work. For an opted-in session, atomically write a private `reporting-session.json` marker containing only a schema version, a local ownership nonce, the current consent revision and the validated app/OS/architecture metadata. No repository information or session contents enter this file. Normal `will-quit` cleanup and opt-out remove the marker when its contents still match the marker written by that instance. A canceled window close does not clear it.

On the next launch, a valid marker matching current consent may produce one `main/unclean-exit` event using the previous app release. Replace it with the new session's marker before attempting delivery. Failed delivery is not queued for retry. An unclean exit can mean a crash, forced termination, power loss or interrupted cleanup; it is a warning, not proof of an application crash. Missing, changed, corrupt, oversized or redirected marker state is never used as arbitrary report content. Unsupported recovery state disables reporting for that session and preserves the original file.

Consent schema version 2 requires a new explicit opt-in for this expanded behavior. Read valid version-1 consent as disabled, preserving its revision so the user can review and save the new choice. Each consent save gets a fresh local nonce; disabling and later re-enabling cannot authorize a marker from an earlier consent period. Neither consent nor session nonces are transmitted. Renewing consent cancels an in-flight attempt from the old generation and resets its delivery status.

Observe main JavaScript exceptions through Node's [`uncaughtExceptionMonitor`](https://nodejs.org/api/process.html#event-uncaughtexceptionmonitor), without replacing default exception handling or inspecting the Error object. A promoted unhandled rejection receives a separate fixed category. If the process exits before asynchronous reporting can run, its interrupted-session marker supplies the generic next-launch summary. Do not add an `unhandledRejection` handler that changes Node's default fatal/warning behavior.

Renderer global `error`/`unhandledrejection` events and the React error boundary submit only one of two literal reason strings. A strict, trusted-frame IPC route fixes the process category to renderer; it accepts no message, stack, filename, process override or destination. Reporting failures are caught to prevent recursive error events. Existing error propagation and default handling remain in place. JavaScript events use error severity, native process failures retain fatal severity, and interrupted-session summaries use warning severity. All existing consent, destination, concurrency, deadline and attempt limits still apply.

Tests cover marker ownership, original-release recovery, clean shutdown, consent changes, migration, corrupt/symlinked files and renewal cancellation. Linux desktop acceptance generates real renderer errors, unhandled promise rejection, a main exception, a Git-utility crash, a renderer crash and main-process SIGKILL against the local trusted HTTPS receiver. Private sentinel strings in the exceptions must not appear in any report. Restart after normal shutdown must not produce an interrupted-session event, and the disconnected default build creates neither consent nor session-marker files.

This does not capture native startup failures before JavaScript/reporting initialization, preserve reports across a failed disk write, identify the cause of an abrupt exit, collect native dumps or detailed stacks, or guarantee delivery before termination. Main promise rejections are observed only when Node promotes them to monitored exceptions. Worker-specific JavaScript failures and every React failure path are not separately exercised. Actual Sentry project acceptance, Windows/macOS runtime evidence and beta feedback remain outstanding.

## Saving consent during marker failures and shutdown

Opt-in prepares the marker for the new consent revision before publishing that revision. If marker creation fails, a first opt-in leaves the saved preference off. Opt-out stops delivery immediately and saves the off preference before attempting marker cleanup. If someone changed the marker, OpenKraken preserves it and the dialog confirms that reporting is off. An unverifiable marker at startup also stops reporting for that launch. The dialog can still save an off preference when the saved consent itself is verifiable. Shutdown waits for an accepted opt-out to finish.

Linux desktop tests use a temporary HTTPS receiver. They exercise a marker changed while running, an unreadable marker at startup and a failed first opt-in. Each test restarts the desktop app and checks both its setting and the receiver. The native CI matrix also runs these tests. The Git utility signal test runs on POSIX platforms. For a forced renderer failure, the receiver must get a summary when Electron reports a crash and none when Electron reports a kill. [Electron renderer termination behavior](https://www.electronjs.org/docs/latest/api/web-contents#contentsforcefullycrashrenderer)

## Failures while the main process is starting

The primary instance registers its exception monitor and Electron child-process listener immediately after starting the reporter. An observed failure can arrive before the profile read completes. The reporter remembers the current consent generation and waits for that read and startup validation. It sends only if the saved consent applies to the configured destination and the generation still matches. A first opt-in cannot authorize an earlier failure. Closing or revoking during the read keeps reporting disabled.

The Linux Electron fixture throws a main-process exception on the first tick after loading the real entry point. A second fixture emits Electron’s GPU termination notification at the same point. Each exercises a fresh profile, a restart after opt-in, and a restart after opt-out against a local HTTPS receiver. Failures before monitor registration, and process death before either delivery or session-marker creation, remain outside this coverage.

## Sandboxed preload exceptions

Electron can notify the main process when a preload script throws before the renderer can use its bridge. The primary window registers a `preload-error` listener before loading the document. It records the existing renderer exception category in local diagnostics and passes only that category to the consent-checked reporter. The script path and exception object stay outside both records.

The Electron test registers a sandboxed preload script that throws during window startup. The loopback HTTPS receiver gets one renderer exception summary on an opted-in restart and none on a fresh profile or after revocation. The test checks the envelope for private strings from the script path and exception.

## Fatal desktop initialization errors

The packaged entry selects the channel profile, obtains the single-instance lock and starts consent validation before loading the diagnostics and desktop modules. Loading the desktop synchronously keeps its macOS URL listener in the initial turn. Main exception and child-process monitors can now see failures during desktop module evaluation. Secondary instances quit before creating a reporter or session marker.

A synchronous failure loading the desktop, or a rejection during ready-time initialization through the first window's document load, displays a fixed startup error. After dismissal, the primary exits with status 1. It allows up to six seconds for the existing consent-checked report attempt and local cleanup. When initialized, local diagnostics record the fixed process and reason even with reporting off. Exception text, document paths and stacks are excluded. The saved consent revision and reporting destination still govern transmission. A document navigation canceled by closing or reloading the window is expected. The app can quit normally while the first document is loading.

Linux Electron tests trigger a child-process event before the desktop module finishes loading, throw during that module's evaluation and redirect the initial navigation to a missing local document. The two fatal fixtures assert the exit status, removal of the reporting marker, bounded local diagnostic contents and successful reuse of the profile. A separate fixture quits during the first navigation. Native failures before the bootstrap can execute, immediate process death before the marker is durable, and a page whose document loads but whose application script fails remain outside this coverage.
