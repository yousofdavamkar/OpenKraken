# 0067 — Worktree management

## Decision

The Git service owns worktree discovery and creation through `git worktree list --porcelain -z` and `git worktree add`. A separate Worktrees dialog is available from the toolbar and command catalogue. It shows the main/current checkout, branch or detached HEAD, commit, changed-file count, lock reason and stale registration information. Unavailable checkouts remain visible. Reading another checkout's status verifies that its Git common directory still belongs to the opened repository. Bare and unborn repositories keep their distinct states.

Paths come from Git or a main-process native directory picker. Renderer requests select a registered worktree by a service-derived identifier and inventory revision; they cannot supply an open path or creation destination. Opening rechecks inventory membership, availability and the common directory. The revision hashes Git's NUL-delimited inventory, including HEADs and lock/prune metadata. Status changes alone do not invalidate opening or creation because neither operation discards working files. Inventory reads are bounded to 256 entries and 4 MiB, with an 8 MiB status cap per worktree and the existing bounded process pool. Paths must round-trip through UTF-8; undecodable inventories fail explicitly rather than redirecting operations through replacement characters.

Creation offers a new branch at an explicit commit, an existing local branch at its reviewed tip, or detached HEAD at an explicit commit. Git validates branch names and commit existence. Existing branches are checked again against the reviewed OID, and Git's normal refusal to check out a branch already in use remains enabled. No force or branch-reset option is exposed. Main asks for an existing empty directory, with native directory creation available. The service canonicalizes it and refuses nonempty folders before invoking Git. Shared-repository writes use the existing common-directory queue and watcher suppression.

Creation does not change the current checkout or automatically open the new one. Refresh updates the inventory and branch controls; the user explicitly opens a listed checkout. Picker cancellation and errors preserve form choices. Git errors or cancellation may leave partial Git-created state; the application never attempts an automatic recursive deletion or branch rollback. Refresh and Git's own worktree tools remain the recovery path. External Git writers are outside the application's queue, so this is optimistic revalidation, not a filesystem transaction.

Lock and unlock use the same reviewed worktree ID and inventory revision, through the common-directory write queue. Lock reasons are bounded to 1,024 characters and reject NUL. These actions work for offline registered checkouts; they only change Git's registration metadata. The main worktree is not a valid target.

Removal requires a separate explicit review of the path, branch/detached state and commit. It never passes force to Git and never deletes the branch. Main/current, locked or unavailable worktrees are refused. The service checks current operation markers, including merge, rebase, sequencer and bisect state, before deletion. A fresh status read includes ignored files as well as tracked and untracked changes. Index flags (`skip-worktree` and `assume-unchanged`) can conceal edits, so they must be cleared and files reviewed before removal. A detached HEAD must be reachable from a local branch, tag or remote-tracking branch. These checks protect work which an ordinary clean-status check would miss. Git's own final removal checks still apply, including submodule restrictions. External writers can race these checks; no cross-process transaction is claimed.

The UI retains the review after an error and does not dismiss it until success or explicit cancellation. Lock review focuses the reason field; unlock and removal focus Cancel. Cancellation returns focus to the originating control. Successful actions restore that control, or the refresh button when removal deleted the row. Focus restoration waits until controls are enabled after the refresh.

Cleanup first runs Git's verbose prune dry run with a fixed expiration timestamp and shows its full report, including malformed registrations omitted from the normal list. Confirmation submits only a service-issued UUID token. The token is repository-bound, expires after ten minutes, and is consumed before execution. At most 32 repository reviews are retained. The service repeats the dry run with the same timestamp, inventory revision and registration metadata fingerprint before executing native prune under the shared write queue. Changed registrations, restored checkout folders and newly locked entries require another review. A missing detached checkout's HEAD must have a retaining branch, tag or remote-tracking ref, checked both during review and confirmation.

The fingerprint covers sorted metadata names and filesystem identities, sizes and nanosecond modification/change times; it is not a file-content hash or a cross-process lock. Traversal is bounded to 10,000 entries and 32 levels, rejects symbolic links and other nonstandard metadata nodes, and requires UTF-8 names. The dry-run report is bounded to 64 KiB. External Git writers can still race final execution. Prune removes registration records, including index and reflog recovery data; it does not remove branches or checkout folders. The UI explains that consequence and advises reconnecting or locking offline checkouts before cleanup. Historical reflog-only commits are not individually retained by this guard. Cleanup review focuses Cancel and restores the initiating control afterward; an empty report disables confirmation.

`rev-parse` metadata normally uses the existing single-query fast path. When newline-containing paths make its multi-value output ambiguous, the repository service reads the two path values separately. Worktree inventory itself always uses the NUL-delimited format.

## Scope and verification

This checkpoint implements list, create, open, lock/unlock, guarded removal and reviewed pruning. Graph worktree WIP rows and other-checkout watch integration remain follow-up work; the worktree feature is not complete yet.

Native Git tests cover locked, missing, dirty, detached, bare and unborn checkouts, Unicode/newline paths, unknown/stale selections, empty-directory requirements, branch-tip revalidation, refusal of duplicate branch checkouts, detached creation and cancellation. IPC tests reject renderer-supplied paths, force options, malformed IDs and arbitrary revision expressions. Electron acceptance covers stale selection recovery, checkout switching, all three creation modes, native picker cancellation and failed creation with retained form choices. The current platform is Linux; these results do not establish macOS/Windows runtime acceptance.

Management tests cover lock reasons, stale reviews, offline locking/unlocking, refusal to remove main/current/locked checkouts, untracked and ignored content preservation, hidden tracked edits behind both index flags, unreferenced detached commits and clean-index pending merges. Successful removal retains the branch and its tip. Electron acceptance cancels a review, creates a file after review and verifies refusal with the bytes intact, then removes a clean checkout and verifies branch retention. It also checks review focus, focus restoration after cancellation and success, and native menu regression behavior.

Prune tests cover preservation of live and locked checkouts and branches, consumed/foreign/expired tokens, metadata changes, restored folders, detached HEAD retention revalidation and malformed registrations absent from the normal list. Electron acceptance cancels cleanup, rejects a review after an external lock, successfully prunes the stale registration after a new review, and verifies retained branches, locked registrations, focus and empty-cleanup behavior. IPC tests reject caller-supplied paths, cutoff timestamps, reports, candidate lists and force flags.
