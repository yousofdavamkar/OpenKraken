# Reviewed direct PR merge

The PR detail panel offers a direct merge review for open, non-draft GitHub/GHES pull requests. Opening the dialog fetches repository merge settings and fresh PR details. Only explicitly advertised merge-commit, squash and rebase methods are offered. An archived repository or explicitly denied push permission blocks submission. Missing push-permission metadata remains unknown and is labeled accordingly; it is not presented as verified access. Missing method flags do not imply support.

The preview shows the configured host, repository, source/target branches, full head/base commit IDs and provider mergeability state. Closed/merged, draft, conflicting or not-yet-calculated PRs cannot be confirmed. Users may refresh the preview when the provider is still calculating. Mergeability does not certify required checks/reviews; the provider applies its branch rules at the write boundary. Commit-message defaults remain provider-controlled unless the user chooses a bounded custom title/body. Rebase preserves commit messages and does not accept custom message fields.

A separate confirmation names the PR, destination branch and method and explains that this updates the remote branch without an application Undo. Inputs freeze at confirmation. Main reauthorizes the account, rereads repository policy and PR details, and compares both commit IDs plus the head/base ref names before sending. Checking ref names also catches retargeting to another branch at the same commit. The selected method must still be enabled, the PR open/nonmerged/nondraft and mergeable, and the repository writable according to the metadata available.

The direct REST merge request supplies the reviewed head SHA as the provider's conditional-write guard. No queue, bypass, branch deletion or local Git operation is sent. GitHub's direct endpoint does not handle stacked PRs or merge queues; these need a separately reviewed workflow. The newer asynchronous API can act on open downstack PRs, so silently switching to it would exceed this dialog's selected-PR preview. A provider rejection requiring a queue is surfaced without fallback. The base/ref checks are preflight checks, not atomic server conditions: GitHub does not accept an expected base tip/ref for this endpoint, so the target can still advance or change after preflight. No stronger guarantee is claimed.

One PUT is sent for each explicit confirmed action, with no automatic retries. Success requires `merged: true` and a valid resulting commit ID; provider response messages are not rendered. Explicit nonmerge/client/auth/policy/head-mismatch rejections produce sanitized errors and require refreshing the preview. Server failure, cancellation or an invalid acknowledgment after dispatch is uncertain, because the merge may already have completed. The dialog then offers a read-only status check. A provider-reported merged/closed PR cannot be resubmitted; an open result requires an explicit fresh preview and confirmation. The status check reports current provider state, without claiming which actor caused a merge.

The nested modal blocks parent interactions while pending, provides cancellation, preserves custom text after rejection and asks before discarding edits to the method, default-message choice, title or message. Choosing **Keep editing** retains a method-only edit. Closing a completed or uncertain operation refreshes the PR list; otherwise details refresh after close. Application quit/crash recovery of pending external writes and durable message drafts remain M8 work. Stopping a request after dispatch cannot retract a server merge.

Public IPC accepts only strict repository/PR selectors, reviewed commits/ref names, a supported method and bounded optional message fields. Rebase requests with custom messages, unreviewed requests, arbitrary URLs, credentials, queue actions and bypass flags are rejected. These methods remain main-process provider operations and are not accepted by the Git utility.

MSW tests cover GitHub and Enterprise requests, all three methods, exact head guards, stale head/base and retargeted-branch refusal, policy/method/permission changes, closed/draft/conflicting/unknown state, metadata validation, preflight cancellation, server head-race rejection and one-PUT behavior after uncertain acknowledgments. Electron acceptance keeps the real main/preload/UI boundary: method selection, custom message confirmation/preservation, changed-head and disabled-method refusal, server rejection, success/list refresh, lost acknowledgment/status inspection without duplicate writes, and cancelled preview. HTTP and OS protection are synthetic boundaries; no live provider PR was merged.

Public references: [GitHub direct merge](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request), [repository metadata](https://docs.github.com/en/rest/repos/repos#get-a-repository), and [asynchronous merge semantics](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request-asynchronously). Merge queues/stacks, check displays, issues, polling and remaining providers are not completed by this slice.
