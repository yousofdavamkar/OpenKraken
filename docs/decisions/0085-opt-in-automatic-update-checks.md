# 0085 — Opt-in automatic update checks

Signed release checks and AppImage installation exist, but requiring a manual check leaves update discovery incomplete. Automatic checking is a separate, default-off preference. It contacts only the build-owned HTTPS feed described in ADR 0082; it does not download or install packages. The Updates dialog names the server and requires an explicit checkbox action. No feed means no control, update requests or update storage initialization.

Main persists the preference in a private, bounded `automatic-checks.json` in the update directory. Its schema binds the exact feed/key configuration, enabled state, consent revision and next deadline. Writes are serialized, synced and atomically renamed from a fixed scratch file. User changes require the current revision; scheduled deadline updates preserve that revision. Corrupt, redirected, externally changed or incompatible settings stop automatic work while preserving affected files. They do not authorize silently resetting trust or consent. The existing signed-release watermark remains independent and unchanged.

The first enabled check is due after 30 seconds. On application startup, automatic work waits for startup recovery and at least 30 seconds, then respects the saved deadline. Main records the next deadline ten hours ahead before a scheduled attempt so repeated restarts or failures cannot produce a tight request loop. A manual check also advances that deadline. Timers are bounded and unreferenced, stop on shutdown, and never reset on renderer remount. Wall-clock changes can delay a check; there is no catch-up burst. Closed applications do not run background services.

Scheduled checks use the existing signature, expiry, rollback, TLS, byte-limit and timeout enforcement. They neither interrupt another updater operation nor discard a verified download or prepared installation. If a scheduled slot occurs during one of those states, it advances to the next interval. Turning automatic checks off aborts an active scheduled request but leaves a user-started transfer running. Explicit transfer cancellation remains available separately.

The toolbar displays a version-availability indicator with an accessible description. While automatic checking is enabled and the dialog is closed, the renderer reads main's status at most every 30 seconds; the renderer never schedules network checks or chooses a destination. Opening the dialog shows current status immediately. The existing download and native installation/restart consent flows remain authoritative.

Controller tests use real preference files and signed metadata with an injected transport and clock. They cover default-off behavior, revision checks, persistence, startup grace, ten-hour intervals, restart/remount deadlines, protected downloads, external preference changes and selective cancellation. Electron acceptance uses a real HTTPS fixture and real startup/notice timers, verifies saved consent across restart, observes background discovery while the dialog is closed, and turns the preference off before another restart. Test-only keys and CA trust remain confined to fixtures.

This does not implement failed-startup rollback, trust-root migration, production publishing, code signing or native installation for the other package formats. Same-account attackers can modify the private profile; this preference is not a security boundary against that attacker. Filesystem permissions and runtime behavior outside the existing Linux acceptance require native platform verification.
