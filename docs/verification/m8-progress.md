# M8 progress — hardening and release

M8 remains in progress. The current checkpoint adds verified predecessor restoration after failed AppImage execution or exit before startup confirmation, with a persistent recovery notice. It follows opt-in automatic checks, signed downloads and desktop installation/restart. It does not establish release completion or close the remaining [M6](m6-progress.md) and [M7](m7-progress.md) scope.

## AppImage startup exit recovery

The native recovery implementation (`95b7787`) binds the predecessor and transaction journal hashes from main's prepared transaction. It observes the replacement in a reserved process group, checks that ordinary replacement processes have exited, then revalidates the installed bytes, predecessor, journal and private directory before atomic restoration. It launches the predecessor once with the same profile and leaves journal cleanup to that app's normal startup. Changed targets/backups/journals, unexpected files and uncertain process state preserve recovery files. No Git operation is retried and the signed-release watermark is retained. See [ADR 0086](../decisions/0086-appimage-startup-exit-recovery.md).

A fixed private notice survives restart and background checks until explicitly dismissed. Main validates notice data before exposing it, and refuses dismissal if the file changed. The toolbar and Updates dialog show that a prior update failed and the previous version was restored. Malformed notice data cannot falsely report restoration. The notice contains no path, repository, account or exception data.

Windows amd64 and macOS arm64 native-helper cross-compilation passed; this is not runtime evidence. ## AppImage installation transaction

The file adapter (`c51af0c`) stages a bounded replacement next to an owned AppImage, rechecks its signed digest/size and format/architecture, writes a durable recovery journal, retains the old inode, and atomically replaces the original filename. Startup acknowledgement can remove the retained image only when the installed hash and running version match. Explicit rollback restores the exact retained predecessor and refuses an externally changed target. Interrupted staging and cleanup are recoverable; unknown, redirected or invalid files are preserved. See [ADR 0083](../decisions/0083-appimage-update-file-transactions.md).

At this adapter-only checkpoint the desktop install/restart flow was not connected. The later desktop handoff above adds target discovery, signed-release/cache revalidation, busy/unsaved-work handling, accepted shutdown/restart and startup acknowledgement. Automatic startup failure detection remains open. No installed user application was replaced; native acceptance uses disposable, locally built fixtures.

While replacement happened, the old process continued reading its original mounted/extracted files. New launches observed the expected replacement and predecessor versions. This proves the file/runtime transaction for those fixtures, not Electron relaunch or complete automatic update acceptance. CI now invokes the native check; remote execution is unverified.

## Signed update checks and downloads

## Native command supervision

The Git utility configures the bundled native helper before starting Git discovery or repository commands. Each command receives a supervisor that retains its process-group identity on POSIX or joins a private Windows Job Object. Parent death stops ordinary active descendants. Existing argument vectors, environment isolation, streamed output, cancellation and deadlines remain in place. See [ADR 0071](../decisions/0071-native-process-supervision.md) for platform behavior and limitations.

A native fetch to a stalled local HTTP endpoint reproduced the leak before the change: its connection remained open after the Git utility died. The same regression now observes closure before the server releases any connections and reopens the repository through a replacement service. A Linux commit-hook fixture kills the utility while a signal-ignoring hook and its child are active; both stop and HEAD, index entries and staged content remain intact. This particular fixture does not establish rollback or lock recovery for arbitrary interrupted writes.
